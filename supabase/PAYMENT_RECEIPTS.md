# Payment receipts and Student ID emails — status

## Findings (traced 21 Nov 2026)

1. **Payment is simulated.** `src/components/auth/EnrollmentPanel.tsx` → `processPayment`
   (`src/context/AuthAndCourseContext.tsx`) creates an `AIW-ADM-…` reference **in the browser** and
   `src/services/paymentService.ts` stores it in the student's Supabase **user metadata**
   (`aiw_simulated_payment`), which the student can edit. No payment gateway, webhook or server-side
   verification exists, and no money is charged (Batch 1 offline is ₹0; online mode is locked).
2. **No email infrastructure.** The only emails are Supabase Auth's built-in confirmation / reset emails.
   There is no email provider (Resend, SendGrid, SMTP…), no `supabase/functions` (edge functions) and no
   email secrets.
3. **Student ID** is generated by the database (`public.student_registrations.student_code`, APW + 7
   digits, migrations `20261121000300` + `20261121000700`) at registration — before and independent of
   payment.

## What was changed (safe parts)

- The post-enrollment screen is now an **"Enrollment summary"**, not an "Admission receipt". It shows
  the Student ID, labels the app-generated reference as an "Enrollment reference" (not a transaction ID),
  and states that no online payment was processed and no email receipt is sent.
- The Student ID is shown (with a copy button) on the dashboard and the profile page.
- **No receipt email is sent.** A simulated payment is never presented as a verified transaction.

## What is needed before real receipts can be sent

| Item | Needed from the organisation |
|---|---|
| Payment gateway (e.g. Razorpay) | Merchant account, API key id + secret, webhook signing secret |
| Issuer details for the receipt | Legal name, address, GSTIN (if applicable), receipt numbering rules |
| Email provider | Account (e.g. Resend / SendGrid / Amazon SES), API key, verified sender domain (SPF/DKIM) |
| Supabase | Edge Functions enabled; secrets stored with `supabase secrets set` (never in the frontend) |

## Design to implement once the above exists

1. **`public.payments`** (server-written only: RLS on, no insert/update grants for `anon`/`authenticated`;
   students may `select` their own rows): `id`, `user_id`, `provider`, `provider_payment_id` **unique**,
   `amount_paise`, `currency`, `status`, `verified_at`, `receipt_number` unique, `receipt_email_status`
   (`pending` / `sent` / `failed`), `receipt_sent_at`, `last_error`.
2. **Edge function `payment-webhook`**: verifies the gateway signature, re-fetches the payment from the
   gateway API, then inserts the row with `on conflict (provider_payment_id) do nothing` — so duplicate
   webhooks are idempotent. Only a verified `captured` payment marks the student paid (replacing the
   user-metadata flag in `PaidGuard`).
3. **Edge function `send-receipt`** (or a step of the webhook): for rows with
   `receipt_email_status = 'pending'`, renders the receipt (student name, Student ID from
   `student_registrations.student_code`, amount, verified date, gateway payment id, program, issuer
   details) and sends it through the email provider; sets `sent` + `receipt_sent_at` only after the
   provider accepts the message, otherwise `failed` + `last_error` (retried later). The status column
   prevents duplicate receipts.
4. Logging: function logs in Supabase (no secrets or full card/UPI data logged).

Until then the receipt flow stays disabled.
